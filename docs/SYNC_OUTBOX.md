# Замороженные запросы и подтверждения — T41c3

storage/sync_outbox.py добавляет API TaskStore для подготовки запросов и хранения
квитанций. Tasks schema **v16**, garden v7/dependencies прежние. Это локальная
инфраструктура без HTTP/аккаунтов/автоматического capture/inbound. SyncBinding
из UUID остаётся маркером контекста, не подтверждением настоящего входа.

## Данные

sync_outbox: intent_id (FK на sync_intents), request BLOB, request_hash, receipt
BLOB/null. Запрос — канонические encode_operation bytes, receipt — канонические
encode_receipt bytes. Plaintext-паролей/токенов/endpoint с ключом здесь нет;
payload содержит только ранее согласованные DTO сущностей. op_id равен
локальному intent.id и не меняется между retry.

SyncBase — явные известные server-generation/target kind/id/revision/epoch.
Происхождение основания обязан подтвердить будущий вызывающий код по
аутентифицированному серверному состоянию. Это не пользовательские часы и не
номер локальной SQLite-записи. Сам тип/кодек не доказывает права/owner сервера.

FrozenRequest содержит seq/intent ID, parsed Operation, неизменяемые raw bytes,
parsed Receipt и её bytes. Bodies скрыты в repr. Чтение повторно проверяет
каноничность, hash, соответствие исходному намерению/контексту и квитанции.
Повреждение блокирует получение, данные не удаляются/не «чинятся» молча.

## Подготовка и зависимости

freeze_sync_intent(id, base=None) работает под BEGIN IMMEDIATE:

- существующий frozen возвращается byte-for-byte, повторный freeze не создаёт
  новый запрос; предоставленное другое основание отклоняется;
- впервые требуется известный SyncBase для цели и поколения; только create
  может использовать предусмотренные протоколом revision=0/epoch=0;
- все указанные предшественники должны иметь сохранённые applied Receipt;
  неполученный/неподготовленный/отклонённый родитель блокирует freeze;
- если раньше в очереди был тот же target kind/id, цепочка должна содержать его
  последнее намерение. Основание берётся из его подтверждения, в том числе через
  промежуточную зависимость другого объекта;
- квитанция другого объекта не становится основанием текущего. Для такой цели
  передаётся свой SyncBase. Явное несовпадение с derived base отклоняется;
- Operation проходит строгий wire-кодек и только затем сохраняется. Например,
  legacy random-root rollover не переписывается скрыто: остаётся намерением до
  правильной подготовки/разрешения producer-ом.

Производитель должен связать последовательные правки одного объекта. При
реальном одновременном удалённом изменении сервер ещё должен проверить CAS/
epoch и вернуть согласованный результат. Библиотека не перепривязывает старое
содержимое к произвольной новой ревизии. Разрешение конфликтов/замена отвергнутых
намерений — отдельный будущий UI/workflow, сейчас они остаются заблокированными.

## Подтверждения и порядок

save_sync_receipt проверяет Receipt против сохранённого Operation: op/device/
server/hash, status, revision и действие с epoch. Сохранение атомарно, повтор
идентичной квитанции idempotent; противоречащий результат не заменяет прежний.
Rejected сохраняется как rejected, а не становится applied. Рабочие задачи,
completion dates, garden и source snapshot при сохранении Receipt не меняются.

get_frozen_sync_request / list_frozen_sync_requests позволяют читать persisted
состояние; неизвестный intent ID вызывает KeyError, известный ещё не frozen
возвращает None. next_sync_sendable — только FIFO-кандидат, не отправка: первый
unprepared/rejected блокирует более поздние строки; applied пропускаются. Можно
подготовить независимый поздний запрос, но candidate API не отправит его раньше
головы. Никакого таймера/backoff/сетевого retry на этом шаге нет.

Все операции используют соединение TaskStore в его worker-потоке, без вложенных
публичных транзакций. Родительский graph остаётся сохранённым; acknowledged
requests пока не компактируются. Не вызывать freeze повторно для replay локального
transform — обычное изменение было записано в intent раньше (SYNC_STORAGE.md).

## Миграция и backup

v15 → v16 добавляет таблицу одной общей DDL-транзакцией, сохраняет binding/
intents/задачи. Сбой откатывает новую таблицу и user_version. Предыдущие valid
v1–14 migration пути и archives v9–15 сохранены; неизвестная схема не маскируется.

Создание/импорт архива очищает только validated staged copy: сначала outbox,
потом intents/binding/sequence, затем compact SQLite-файл. Рабочий request и
квитанция сохраняются без изменения. Вручную составленный импорт с outbox также
не возобновляет старые отправки. Internal before-copy аварийного pair rollback
по-прежнему содержит всю очередь, включая frozen bytes, и восстанавливает её
при сбое. После успешного restore требуется явное новое подключение/preview.

## Ограничения

Настоящие transport/owner/auth, server ledger/CAS, metadata входящего снимка,
полный capture всех изменений, rebase/conflict UI, общий пояс runtime и применение
страниц не реализованы. Основания для первого независимого запроса передаются
явно, не считываются из уже готового inbox: inbox ещё не подключён.
Следующий шаг — opt-in capture ordinary mutations, затем остальные пути/worker.
До inbound остаётся согласование наград сада за новые удалённые выполнения.
Windows/Wayland/standalone/full release audit этим шагом не подтверждены.
