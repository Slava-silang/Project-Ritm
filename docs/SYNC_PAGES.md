# Получение полного снимка страницами — T41b2b2

`integrations/sync_pages.py` — чистый формат и временная сборка. Нет HTTP,
сервера, аккаунтов, outbox, сохранения или применения в пользовательскую БД.
Сущности — SYNC_ENTITIES.md, операции — SYNC_OPERATIONS.md.

Оболочка JSON: ровно `version:1`, `kind:snapshot_page`, `data`.

| Поле data | Контракт |
| --- | --- |
| server_id | UUID поколения сервера |
| snapshot_id | UUID одной попытки чтения |
| set_revision | Ревизия всего набора, строка 0…2^63−1 |
| total | Объявленное число записей всего снимка, строка |
| offset | Число записей до этой страницы, строка |
| cursor | null для первой страницы, иначе курсор её запроса |
| next_cursor | null только у последней страницы |
| entries | Массив записей: revision, delete_epoch, entity |

revision/delete_epoch — канонические целые строками, entity — полная оболочка
из sync_codec. Ревизия записи положительная и не выше set_revision. У removed
ревизия/барьер внутри entity точно совпадают с обёрткой. Курcор — непрозрачная
строка 1–512 символов A–Z/a–z/0–9/_/− (в коде обычный ASCII-дефис), без данных
для входа. Проверка формата курсора не является серверной подписью/авторизацией.

Первая offset=0/cursor=null. Остальные требуют cursor; offset + число entries
не превышает total. next_cursor=null тогда и только тогда, когда достигнут
объявленный total. Пустая промежуточная страница запрещена, пустой снимок
разрешён только одной завершающей страницей с total=0/offset=0.

## Временный сборщик

SnapshotCollector создаётся с ожидаемым server_id. add(page) повторно проверяет
даже типизированную страницу. Все страницы имеют один snapshot_id/set_revision/
total, непрерывные offset, точную цепочку курсоров без циклов. При неправильной
странице временные записи очищаются, сборщик остаётся непригодным: для новой
попытки нужен новый объект. Повтор/перестановка уже принятых страниц отклоняются.
finish() не выдаёт записи до конца цепочки и проверки связей. Результат —
неизменяемый Snapshot, а не команда изменения базы.

В полном снимке проверяются:

- уникальность UUID записей и узлов деревьев, в том числе между страницами;
- отсутствие текущего корня одновременно внутри regular и отдельным task;
- отсутствие живого объекта и отметки удаления с тем же UUID;
- наличие живой категории у каждой задачи с category_id;
- наличие задачи у связанного блока либо минимальной archived_task_title для
  допустимой связи с уже вытесненной историей. Обычные события связи не требуют.

UUID считаются единым пространством для получаемых объектов/узлов. Отметка
удаления узла может ссылаться на отсутствующий старый root: она не требует
загрузки удалённого дерева. Текст у removed не появляется.

Лимиты начального контракта: 50 entries/страница, 2 МиБ UTF-8 на страницу
включая оболочку, 10000 записей и 32 МиБ суммарных канонических страниц на
временный снимок. Превышение — отказ без усечения/частичного результата. Это
предел клиента, не реализованная серверная квота; пользовательские данные при
отказе не очищаются. Большие объёмы требуют отдельной настройки/проверки.

## Что ещё не реализовано

Сервер должен связать курсор с owner, попыткой и set_revision, проверять ревизию
при каждом чтении и разрешать согласованный перезапуск без хранения старых
текстовых снимков. Клиент пока проверяет только объявленную согласованность;
не может доказать, что сервер честно указал total и не пропустил запись.

Общая ревизия снимка не заменяет сравнение с уже применённой локальной ревизией.
Транзакционное применение, ограничения попыток/сети, сохранение pending-правок,
защита от старого полного снимка и собственные таблицы inbox/outbox — T41c.
Наличие полного снимка не разрешает по отсутствию объектов удалять локальную
историю/файлы/корзину. Пустой сервер нового поколения не очищает профиль;
даже принятый пустой Snapshot сам ничего не меняет.

Формат пока только full snapshot; delta-журнал/согласованные эффекты изменений
ещё не закодированы. История регулярных экземпляров (rule_id,day), общая
календарная дата и реальные rollover/CAS/owner остаются отдельными задачами.
Нет подтверждённой межустройственной синхронизации или работающего сервера.
