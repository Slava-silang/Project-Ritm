# Локальные несетевые намерения — T41c1

Tasks SQLite автоматически переходит с v14 на **v15**; garden остаётся v7.
Новые таблицы пусты до явного вызова storage API. Обычный запуск и прежние
изменения задач не подключают синхронизацию и не начинают запись очереди.
Нет сервера/HTTP/регистрации/токенов/активного аккаунта в интерфейсе.

## Модель хранения

| Таблица | Содержимое |
| --- | --- |
| sync_binding | Одна локальная привязка: owner UUID, device UUID, server-generation UUID |
| sync_intents | seq, уникальный id, context_id, depends_on, target_kind/id, action, desired_json |
| sync_intents_target | Индекс цели и порядка для будущего adapter |

SyncBinding — локальные идентификаторы, не подтверждение входа или прав.
Нет Telegram ID/телефона/email/логина/пароля, endpoint с ключом, access/refresh
токена. Проверка аккаунта и отдельный vault ещё впереди. Текущий API не позволяет
переписать владельца/устройство/поколение: совпадение idempotent, другой контекст
отклоняется без очистки. Явное отключение/перепривязка — будущий отдельный путь.

SyncIntent — несетевое намерение, ещё не замороженный Operation. desired_json
содержит только encode_entity, без произвольных полей. delete/stop_regular
сохраняют null, а не прежний текст. В таблице нет before/after снимков корзины.
Поля CRUD/regular/calendar/history проверяются; для rollover намерение может
ещё иметь локальные UUID — детерминированный request готовится позже при freeze.

Очередь append-only через API: тот же id и те же канонические данные возвращают
прежний seq, другое содержимое отклоняется. depends_on должен уже существовать
в этой привязке, не совпадать с id; чтение проверяет, что родитель раньше в seq.
Цикл/повреждение блокирует чтение, данные не очищаются. Это ещё не обработчик
зависимостей: наличие родителя не означает его подтверждение сервером.

## API TaskStore

- get_sync_binding / initialize_sync_binding — чтение и явная первая запись;
- enqueue_sync_intent — атомарная запись одного проверенного намерения;
- list_sync_intents — порядок/зависимости, без отправки;
- update_task_and_enqueue(id, transform, make_intent) — ограниченный путь для
  ordinary root: задача, completion date, garden source event и намерение в одной
  SQLite-транзакции. Factory получает сохранённый TaskRecord с реальной датой.

Последний метод пока поддерживает put/prune обычной существующей задачи. ID и
payload должны соответствовать записанному результату. Повтор combined local
edit с прежним intent ID отклоняется и откатывается: нельзя заново выполнить
transform под видом retry HTTP. Повторы HTTP будут работать с замороженным
Operation, не с этим методом. Ошибка очереди/несовпадение/отсутствующий родитель
откатывают задачу, completion date и garden journal.

Текущие/бывшие recurrence_occurrences требуют отдельного history adapter и
этим методом не меняются. Создание/удаление/все пути QML/ИИ/календаря/категорий
ещё не охвачены автоматически; старые методы TaskStore не начали вдруг собирать
очередь. Эти API не подключены к UI подключения. Вызывать из storage worker,
без сетевых/долгих действий в callbacks и без вложенных транзакций публичных API.

## Миграция и резервные копии

v1–14 мигрируют в общей BEGIN IMMEDIATE транзакции. Сбой DDL откатывает версию и
новые таблицы; прежние tasks/recurrence/garden identity сохраняются. Более новые
версии по-прежнему отклоняются, неизвестную схему не «лечим» IF NOT EXISTS.
Для synthetic legacy tests удаляются поздние таблицы перед установкой старого
user_version — tests/migration_support.py, не производственное послабление.

При создании архива копируется согласованная пара БД, затем **только staged
копия tasks** лишается sync_intents/sync_binding/счётчика очереди. secure_delete
и VACUUM убирают содержимое освобождённых страниц самого SQLite-файла архива.
Источник не меняется. Это не обещание физического стирания данных SSD/временных
файлов; обычные пользовательские задачи/корзина/материалы остаются в копии.

Проверенный импорт архива также очищает sync metadata в staged базе перед
восстановлением, даже если такой архив был составлен вручную с привязкой.
Обычные архивы схем v9–14 принимаются/мигрируют, v15 проходит прежнюю проверку
точного состава схемы. После restore нужна новая привязка и предпросмотр,
старая очередь не переигрывается. Окно подтверждения это объясняет.

Внутренняя before-копия для аварийного rollback **не очищается**: если замена
пары прервётся, исходные привязка и очередь должны восстановиться вместе с
задачами/садом. Это проверено отдельным сбоем второй публикации базы.

## Что остаётся

Нет frozen-json, op receipt ledger, курсоров/inbox/сетевого worker, применения
страниц, восстановления токенов или SQL-модели серверных ревизий. Источник
TaskStore→LocalData готов в T41c2 (SYNC_SOURCE.md); автоматический захват
всех изменений/заморозка/подтверждения — следующие шаги.
Перед inbound остаётся решение о наградах сада за новые удалённые выполнения.
Это локальные копии, не серверные backups (их пользователь решил не хранить).
Windows/Wayland/standalone и общий выпускной аудит этим шагом не подтверждены.
