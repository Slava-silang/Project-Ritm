# Окружение, запуск и выпуск

На 8 ноября 2026 года T01 и T02 завершены: минимальное QML-окно запускается из исходников и самостоятельной Linux-поставки. Бизнес-функции приложения относятся к следующим задачам.

## Уже установлено на текущем компьютере

Проверено из текущей сессии: Linux Mint 22.3, x86_64, Cinnamon/X11; Python 3.12.3; Git; uv; GCC/G++; make. Стандартный модуль `sqlite3` доступен (SQLite 3.45.1).

В `.venv` установлены PySide6 6.12.0, pytest 9.2.0 и Ruff 0.17.4; группа упаковки добавляет Nuitka 4.2.2, ordered-set 4.1.0, zstandard 0.25.0 и Linux patchelf 0.19.3.0. Версии фиксируются в `uv.lock`. Системный Python не изменён. Для компиляции используются имеющиеся GCC 13, readelf и заголовки Python 3.12.

## Воспроизведение окружения

Из каталога репозитория выполнить `uv sync --locked`. Требуется Python 3.12; `.python-version` задаёт эту ветку. PySide6 — зависимость приложения, pytest и Ruff — группа разработки, устанавливаемая по умолчанию. `.venv` создаётся локально и исключена из Git.

При появлении моделей настроить проверку аннотаций типов с учётом Qt-привязок. Инструменты упаковки устанавливать при T02 отдельно от обычных runtime-зависимостей и фиксировать рабочую конфигурацию.

Системный Python не заменять. Отдельная установка полного Qt SDK обычно не требуется: PySide6 wheels включают библиотеки Qt. SQLite — встроенная локальная библиотека; сервер базы данных устанавливать не нужно. Qt Creator или редактор с поддержкой QML необязателен для командного запуска.

Источник: [Qt for Python: Getting Started](https://doc.qt.io/qtforpython-6/gettingstarted.html).

## Запуск при разработке

Проверенные команды:

```sh
uv sync --locked
uv run ritm
uv run pytest
uv run ruff check .
uv run ruff format --check .
uv run pyside6-qmllint src/ritm/qml/Main.qml
```

Диагностика: `uv run ritm --smoke-test` открывает и закрывает окно автоматически; `uv run ritm --version` выводит версию. Альтернативный запуск: `uv run python -m ritm`.

Из другого каталога: `uv run --project /полный/путь/к/Project-Ritm --locked ritm`. В T01 реальная команда проверена из `/tmp`; оба entrypoint дополнительно проверены тестами из папки с пробелом и кириллицей.

В среде без экрана автотесты используют Qt offscreen и временные XDG-каталоги. Реальный рабочий стол проверять отдельно. Если ограниченная среда агента не даёт доступа к X11, это не означает отсутствия библиотек: проверить реальный запуск в разрешённой пользовательской сессии.

Обычный цикл: изменить Python/QML → выполнить подходящие проверки → запустить интерфейс → сохранить результат. Релизная компиляция при каждом изменении не требуется.

QML загружается относительно пакета, а не текущего каталога. В T01 пользовательские данные ещё не создаются. При добавлении хранилища разработка и тесты должны использовать отдельные профили.

`uv build --wheel` проверен: `dist/project_ritm-0.1.0-py3-none-any.whl` содержит Main.qml. Это Python-пакет, не самостоятельная программа для компьютера без Python.

Источник: [uv: Working on projects](https://docs.astral.sh/uv/guides/projects/).

## Самостоятельная Linux-сборка

Используются `pyside6-deploy`, Nuitka и явный режим standalone. Зависимости упаковки устанавливаются отдельно:

```sh
uv sync --locked --group packaging
uv run --locked --group packaging python scripts/build_linux.py
```

Команда работает из любого текущего каталога при указании полного пути к скрипту и проекта через `uv --project`. Она создаёт рабочую копию `pysidedeploy.spec` в `build/`, поэтому автоматически найденные абсолютные пути не загрязняют отслеживаемую конфигурацию. Установкой пакетов управляет uv; deploy запускается с `--no-install`.

Результат: папка с исполняемым файлом, Python runtime, Qt-библиотеками/плагинами, QML, изображениями и прочими зависимостями. На другом компьютере распространяется вся папка, а не один исполняемый файл из неё. Отдельный установленный Python пользователю не нужен, но остаются требования к ОС, архитектуре и системным библиотекам.

Nuitka компилирует Python-код, сохраняя зависимость от среды выполнения Python/libpython. Это не превращает всё приложение в программу без Python runtime.

Точка входа упаковки — `src/main.py`, вызывающая тот же `ritm.app:main`. QML включается в `ritm/qml`, относительно пути скомпилированного модуля. Версия хранится в `ritm.__version__`; Hatchling получает метаданные из этого же источника. Исполняемая программа не зависит от наличия метаданных установленного Python-пакета.

После успешной сборки:

- `dist/ritm-linux-x86_64/ritm.bin` — исполняемый файл;
- `dist/ritm-linux-x86_64/` — вся поставляемая папка;
- `dist/ritm-0.1.0-linux-x86_64.tar.gz` — архив этой папки;
- одноимённый `.tar.gz.sha256` — контрольная сумма;
- `build/compilation-report.xml` — локальный отчёт Nuitka.

Версия и архитектура в именах архива определяются скриптом. Папки build/dist/src/deployment исключены из Git. Скрипт проверяет запуск до замены предыдущего результата; окончательную переносимость дополнительно проверяет отдельная команда ниже.

Запуск пользователем из папки программы:

```sh
./ritm.bin
```

Папка передаётся целиком. Python, uv, Qt SDK и Docker конечному пользователю не нужны. Остаются системные графические библиотеки и совместимая Linux-система; Windows требует своей сборки.

### Проверка переноса и чистого окружения

```sh
uv run --locked --group packaging python scripts/check_linux_build.py --relocation-only
uv run --locked --group packaging python scripts/check_linux_build.py --build-image
```

Первая команда проверяет настоящую копию программы в папке с кириллицей и пробелом, версию и загрузку QML. Вторая дополнительно создаёт тестовый Ubuntu 24.04-образ и запускает бинарный файл без установленного Python, исходников и сети, от непривилегированного пользователя с read-only поставкой. Docker используется только для разработческой проверки. С `--directory` можно проверить папку, извлечённую из архива.

Системные библиотеки тестового стенда перечислены в `packaging/linux/Dockerfile.smoke`, включая выявленную зависимость QtNetwork от `libgssapi-krb5-2`. Этот контейнер проверяет offscreen-запуск. Настоящий X11/Wayland проверяется отдельно; наличие Qt-плагина не доказывает поддержку всего рабочего окружения.

### Особенности среды сборки

Nuitka 4.1.1 воспроизводимо завершала бинарный файл с SIGABRT при кириллице в пути до входа в приложение. Проверка переноса добавлена до изменения инструмента; используется ветка Nuitka 4.2 с зафиксированной версией в lock-файле.

На 4.2.2 проверка прошла, включая реальный X11 после распаковки в кириллическую папку и отдельный контейнер без Python. Архив текущей сборки — 93 383 160 байт (около 89 МиБ), распакованная папка — около 288 МиБ. Размер и контрольная сумма меняются при пересборке; актуальный SHA256 записывается рядом с архивом. Эти результаты не подтверждают запуск на всех Linux-дистрибутивах.

В ограниченной среде агента служебный `ldd` вызывал 32-битный загрузчик, заблокированный с SIGSYS. Такая сборка останавливается и повторяется с разрешённым доступом к средствам сборки; система и код Nuitka вручную не изменяются. При обычном локальном запуске из пользовательского терминала эта особенность ограниченной среды не применяется.

Предупреждения deploy об отсутствии необязательного `.pyproject`, повторном включении Main.qml и неиспользуемой Linux-иконке в standalone-режиме сами по себе не означают успешную или неудачную сборку: результат проверяется реальным запуском. `uv build` создаёт Python-дистрибутив и не заменяет standalone.

В Linux для упаковки могут потребоваться readelf, patchelf, заголовки Python и компилятор. Часть устанавливается инструментами в окружение; необходимость системных пакетов проверять по фактической диагностике. При Windows-сборке проверить поддерживаемый компилятор и средства анализа DLL. Вручную заранее устанавливать полный набор SDK на Linux не требуется.

Источники: [pyside6-deploy](https://doc.qt.io/qtforpython-6/deployment/deployment-pyside6-deploy.html), [Nuitka: User Manual](https://nuitka.net/user-documentation/user-manual.html).

## Форматы выпуска

Текущий артефакт — standalone-папка Linux в архиве. Позднее можно выбрать удобную оболочку: например, AppImage для Linux и установщик/portable-папку для Windows. Выбор формата сам по себе не является доказательством переносимости.

Сборки готовить отдельно в соответствующей ОС и для целевой архитектуры: Linux-артефакт не заменяет Windows-артефакт. Сначала проверить минимальную упаковку, потом полный состав. Зависимости Linux могут требовать сборки на достаточно старой поддерживаемой базе; обещание «на любом Linux» не давать.

## Проверка релиза

- Запустить в чистом поддерживаемом окружении без средств разработки и исходников.
- Проверить ресурсы, Qt-плагины и запись данных в пользовательский профиль.
- Пройти сценарии TESTING, включая вложения и восстановление копии.
- Зафиксировать точную ОС/архитектуру, формат, версию, ограничения и контрольную сумму артефакта.
- Перед публичным распространением выбрать лицензию проекта и проверить требования реально используемых зависимостей. Публикация согласуется отдельно.

API-ключ поставляется самим пользователем в настройках. Без ключа локальные задачи, календарь, таймер и обычные реакции компаньона работают.
