# Источник TaskStore → LocalData — T41c2

`storage/sync_source.py`, mixin TaskStore, готовит данные для первоначального
предпросмотра. Не подключает аккаунт, не отправляет запросы, не изменяет очередь
и не применяет входящие. Tasks v18/garden v7; зависимости прежние. Source не читает также capture/presence.

## API и снимок

read_sync_source(calendar=None) выполняет одно явное SQLite BEGIN-чтение.
Первый SELECT корней закрепляет snapshot; деревья, completion dates, категории,
recurrence metadata и календарь читаются в том же snapshot. Даже writer в другом
WAL-соединении не смешивает старые даты с новым телом задачи. Вложенная транзакция
запрещена до начала чтения — внешний незавершённый write не коммитится/не откатывается.

После завершения чтения кодек проверяет/канонизирует immutable DTO, уже без
удержания read-lock. Ошибка не исправляет профиль. Неизвестная completion date
сохраняется null. Ошибки повреждённых полей не включают исходные значения;
guard незавершённого restore сохраняет своё сообщение.

prepare_sync_preview(now, calendar=None, selected_completed=None) передаёт
полученный LocalData в project_local. Результат — данные предложения, не QML-
диалог/разрешение отправки. CompletionSelectionRequired с UUID вариантов
доступен будущему UI без потери признака неизвестных дат. До первого импорта
по-прежнему нужны локальный backup, предпросмотр/выбор и подтверждение.

Общий CalendarRecord передаётся явно; source не читает настройки подключения,
не выбирает системный пояс и не записывает его. Для готовой проекции активных
regular общий пояс обязателен. Сам read_sync_source может вернуть ещё не
подключённый LocalData без этого параметра для последующего выбора UI.
Вызывать из storage worker, а не из GUI потока. Генерация наступивших повторов
должна происходить обычным отдельным действием приложения; чтение их не создаёт.

## Правила источника

- Загружаются живые корни nodes; skipped root IDs определяются по metadata до
  get_task: старое тело skipped вообще не читается. Блоки этих корней исключены.
- Текущие regular включают waiting/future templates, которые обычный list_tasks
  не показывает. Проверяется согласованность rule/task/day/state. Current
  передаётся внутри агрегата, projection убирает дубли обычных TaskRecord.
- Прошлые выполненные slots с сохранённой связью дают OccurrenceRecord, stable
  history_id(rule, day), прежний Task ID и реальную/неизвестную completion date.
- Reopened incomplete slots и прежние slots с вручную назначенным deadline
  остаются ordinary: важные поля пользователя не выкидываются ради history DTO.
- Категории читаются из categories, блоки — обычным live list_work_blocks;
  deleted-root blocks уже скрыты. Окно 30 дней/подписи и лимит 50 выполняет
  project_local. На этапе read набор не усекётся молча.
- Deleted IDs — только ещё существующие task_identities без живого корня.
  После permanent purge identity/блоки могут быть удалены; source не выдумывает
  забытый UUID и не восстанавливает его из before_json. Отсутствие объекта — не
  приказ удалить его в облаке. Будущий capture обязан записать delete intent
  до purge; уже сохранённые intents живут отдельно от task identities.

SQL источника не читает trash/before_json/after_json, attachments/materials,
focus/garden/assistant, sync_binding/sync_intents. Имена/тела удалённых задач и
файлы не восстанавливаются. Валидация timezone может читать системную tzdata,
пользовательские файлы не открываются. Связь source→LocalData не является
проверкой владельца сервера или сети.

## Исправление metadata при текущих действиях

Отключение текущего regular удаляет только его связь occurrence вместе с rule:
завершённый current теперь действительно ordinary, а не ошибочная история.
Удаление current перед архивацией также отсоединяет эту связь; restore
возвращает ordinary и не возобновляет правило. Предыдущие исторические slots
того же rule ID сохраняются. Их archive/restore сохраняет day и дату completion.
Задачи/подзадачи/вложения/даты не очищаются этим исправлением, всё в прежней
SQLite-транзакции. Новая миграция не нужна.

Старые metadata rows нельзя однозначно отличить задним числом: отсутствующий
rule может означать старую историю или выключенный current из прежней версии.
Source читает существующую связь как сохранённую историю, не угадывает и не
чинит её во время read; Task ID/тело/дата не теряются. Первоначальный preview
должен показывать происхождение. Полный capture/detachment истории при reopen
и последующем recomplete после подключения ещё T41c: этот source не является
двусторонним применением или ретроспективной миграцией intent пользователя.

## Дальше

Источник не создаёт binding/intent/frozen Operation, не выбирает конфликт с
облаком и не реализует transport. Подготовка/заморозка запроса, зависимости и проверенные receipts теперь
сохраняются в локальной очереди (SYNC_OUTBOX.md). Затем автоматический
capture всех путей/worker/inbox; до inbound остаётся решение о наградах сада.
