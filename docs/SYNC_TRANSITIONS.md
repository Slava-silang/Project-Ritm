Текущие storage/chain/retirement semantics — SYNC_PREPARE_LOOP.md,
SYNC_REGULAR_PLAN.md и SYNC_RESCHEDULE.md; исходные planning remarks ниже
сохраняют историю контракта pure DTO, а не статус нынешней реализации.

## Записи и общая дата

CalendarRecord, kind=calendar_settings: ровно id (UUID), timezone (доступный
ключ ZoneInfo, до 128 ASCII-символов). Уже существующая зависимость tzdata
обеспечивает базу поясов; при недоступном ключе отказ, без подмены UTC/местным.
На аккаунт один такой объект. Операции только create/put, удаление настройки
обычной командой не поддерживается. Это общая настройка расписаний, не
синхронизация всех настроек desktop.

calendar_day(settings, aware_datetime) переводит переданный момент в этот пояс
и возвращает календарный день, без чтения часов/пояса ОС. DST не превращается
в интервал N×24 часа. Сервер в будущем передаёт свой момент времени.

OccurrenceRecord, kind=occurrence: id, rule_id, day, current (тело TaskRecord).
День — запланированный, не день фактического выполнения. id обязан совпасть с
uuid5(rule_id, "history:"+ГГГГ-ММ-ДД). current завершён, без deadline; неизвестная
completed_at остаётся null. Существующие случайные UUID desktop-дерева
сохраняются: стабильный ID истории отделён от ID задачи и узлов.

Самостоятельная запись истории не требует живого правила — старое правило
могло быть отключено/заменено. Полный снимок проверяет, что при наличии того же
правила день истории раньше current_day и находится на его сетке. Нельзя
одновременно вернуть тот же корень как ordinary task/текущий regular/history.
Два экземпляра одной пары (rule_id, day) имеют один id и обнаруживаются как дубль.
В снимке с активными regular обязателен ровно один CalendarRecord.

removed/occurrence содержит root_id исходной задачи; это только идентификаторы,
ревизия/барьер/reason, без старого текста. Допустим retention — локальная история
не обрезается. Такой root_id нельзя одновременно вернуть живой задачей в том же
снимке. Операции occurrence используют общие create/put/restore/delete/prune;
реальная проверка владельца/предшествующего состояния ещё серверная задача.
Снятие completion старой истории требует явного выхода в ordinary task с
сохранением ID/барьеров, а не отправки незавершённой occurrence — реализовать в T41c.

## Чистый план перехода

plan_regular_effects(before, operation, receipt, settings, moment) принимает
известный серверный SnapshotEntry с RegularRecord. Требует проверенную applied-
квитанцию, точные base_revision/epoch, новую ревизию и тот же rule ID. Возвращает
RegularEffects: квитанция и оба эффекта одной ревизии. Ни SQL, ни сетевых вызовов,
ни отправки или изменения профиля нет. Это не подтверждение настоящей записи
и не авторизация: доверенное состояние/owner/сервер проверяет будущий вызывающий код.

| Действие | Эффекты, которые надо применить вместе |
| --- | --- |
| rollover, прежний завершён | Новый regular и одна occurrence прежнего слота |
| rollover, прежний не выполнен | Новый regular и task-retention отметка прежнего корня без текста |
| stop_regular | Отметка удаления правила и неизменный текущий TaskRecord как ordinary task |
| delete regular | Две отметки user_deleted: правило и текущий корень; без дерева |

rollover требует последнего наступившего дня по общему поясу и точного
совпадения с rollover_record прежнего серверного шаблона. Недостаточно одного
детерминированного UUID: неподтверждённая правка шаблона отклоняется. Предыдущий
слот не меняется, поздняя completion остаётся с исходным запланированным day.
Остальная история не удаляется эффектами; retention учитывает общий
лимит 50 завершённых ordinary+прошлых occurrence, а не 50 для каждого вида.
По принятому уточнению текущие экземпляры активных расписаний вне этого лимита.

Повторный вызов с теми же аргументами возвращает тот же план. Реальный сервер
сначала ищет постоянную квитанцию op_id/hash и только для новой команды проверяет
CAS/строит план/применяет все эффекты одной транзакцией. После применения старая
команда не пересчитывается на новом before. Здесь нет replay ledger или SQL-
транзакции. Полные страницы уже могут представить итог, отдельный delta-формат
не вводился. При записи запрещено опубликовать лишь половину эффектов.

## Зависимости offline — правило для T41c

Локальная правка/очередь сохраняются атомарно, но неподготовленное намерение
ещё не является замороженным сетевым Operation. Намерению можно заранее
назначить локальный ID/ссылку на предшественника. До первой отправки Operation
готовится только при известном основании; потом op_id/payload/hash/основание
не меняются при retry. Это уточнение прежнего общего слова «операция» в плане.

Зависимый rollover/stop/delete ждёт applied-квитанции своего предшественника
и строится на ней, а не на произвольной последней ревизии сервера. Квитанция
проверяется против исходного запроса. Rejected-предшественник блокирует
зависимые намерения; запрещено молча перепривязать старое дерево к новому epoch.
Порядок/перезапуск/промежуточные состояния ещё надо реализовать и проверить в outbox.

За долгую работу offline могут появиться завершённые старые слоты. Нельзя
выкинуть их при сведении очереди к последнему regular: они передаются как
история по (rule_id,day), с сохранением локальной истории. Устаревший уже
отправленный rollover не переписывается: остаётся отклонённым для разрешения.
Чистый planner сейчас не принимает старый промежуточный день вместо актуального.
Подготовка несетевых намерений/импорт истории/разрешение конфликтов — T41c,
не реализованная очередь. Нельзя считать offline-цепочки проверенными этим DTO.

## Проверки и границы

Новые entity-векторы calendar_settings/occurrence и полный regular_history
с поздним завершением. Проверки в tests/test_sync_transitions.py. Поддержка
чтения новых kinds требуется до соединения: это расширение неопубликованного v1,
старый строгий клиент должен отказать, а не отбросить новые записи.
Схемы tasks v14/garden v7 и зависимости неизменны. UI/desktop-генератор со
случайными UUID пока не подключены к этим планам; реальной синхронизации нет.
