# Локальные переходы регулярных задач — T41c5a

Tasks schema v19, garden v7, зависимости прежние. Это ограниченная часть T41c5:
надёжное сохранение локальных фактов до подготовки сетевых команд. HTTP, inbound,
аккаунты, общий серверный пояс и UI подключения пока не включены. Флаг capture
из T41c4 по умолчанию выключен и от миграции не включается.

## Зачем отдельные факты

Desktop создаёт следующий экземпляр со случайными UUID. Сетевой rollover требует
детерминированных UUID и последнего наступившего дня, известной серверной базы и
квитанции предшественника (SYNC_TRANSITIONS.md). Нельзя просто заморозить каждый
локальный переход в такой Operation: после нескольких offline-дней промежуточный
rollover устареет, а выполненные экземпляры потеряются при схлопывании очереди.

`storage/sync_regular_capture.py` сохраняет неизменяемые типизированные снимки
до/после перехода. Будущий adapter должен сначала сохранить выполненные слоты
как OccurrenceRecord по (rule_id,day), разрешить соответствие local/server UUID,
смену типа/правила, зависимости и CAS. Этот adapter ещё не реализован; факты не
являются готовыми Operation/SyncIntent и напрямую не отправляются.

## Хранение и порядок

`sync_regular_changes`: возрастающий seq, уникальный UUID id, context_id FK
на binding, after_intent_id FK на последнюю обычную очередь в момент изменения,
kind, rule_id, root_id, before_json/after_json. Снимки — строгий codec v1
RegularRecord/TaskRecord; тела исключены из repr. after_intent_id — маркер
взаимного порядка двух локальных журналов, не applied receipt или готовая
сетевая dependency. seq задаёт порядок самих regular facts.

| kind | Снимки |
| --- | --- |
| save | Предыдущий RegularRecord/ordinary TaskRecord либо null; новый RegularRecord |
| rollover | Прежний и новый RegularRecord того же правила, разные корни и возрастающий день |
| stop | Прежний RegularRecord и итоговый ordinary TaskRecord |
| delete | Только UUID правила и текущего корня, оба тела null |

Изменение названия/подзадач/выполнения текущего regular через общий `_write_task`
пишет save. Дата выполнения читается в той же транзакции и сохраняется вместе с
запланированным днём; неизвестная дата не выдумывается. Удалённые дочерние UUID
видны из before/after для будущего prune. Неизменный снимок не создаёт событие.

Создание/редактирование/смена расписания, ordinary→regular и stop пишутся после
обновления метаданных, но до commit. При смене расписания оба rule UUID сохраняются
в before/after. Одновременная правка и stop не теряет отредактированное тело.
При rollover сохраняется завершённый прежний слот целиком; незавершённый также
фиксируется как прежний шаблон, но не становится выполненной историей. Пропуск
сразу до последнего дня не создаёт промежуточный backlog. Активация waiting в
свой день без смены DTO не создаёт дубликат.

Все hooks работают в существующей SQLite-транзакции вместе с деревом, датами,
правилом, membership, trash, garden event и отметками. Ошибка даже после INSERT
факта откатывает весь переход. Origin guard T41c4 и выключенный capture исключают
запись; выключение не стирает существующие факты.

`list_sync_regular_changes()` читает один согласованный snapshot, проверяет
контекст, UUID, codec и соответствие типов/корней/дней. Повреждение отклоняется,
данные не удаляются. Внешняя активная транзакция отклоняется до BEGIN, без её
commit/rollback. Чтение источника синхронизации эти таблицы не использует.

## Барьер до готовности

Наличие regular facts блокирует `next_sync_sendable()`, включая уже подготовленные
обычные команды. Они не обходятся как будто regular-изменений нет. Freeze по
явному storage API всё ещё возможен, но это не отправка; готовый транспорт пока
отсутствует. Удалять журнал вручную ради снятия барьера нельзя.

T41c5b ниже добавляет history/reopen/detach/stop/restore в тот же журнал.
Подготовка/подтверждение/очистка facts остаются T41c5c. Корни не становятся
ошибочными plain task intents. Сеть нельзя включать до полного покрытия этих
путей, календаря/категорий/AI и разрешения зависимостей. Поведение локальных
задач/повторов не изменено. До inbound согласовать награды сада.

## Копии и миграция

v17→18 добавляет одну пустую таблицу одной транзакцией, сохраняя прежний флаг и
данные; DDL failure откатывается без повышения версии. Публичные backup/import
очищают facts и их sequence перед остальной sync metadata только в staged-копии.
Рабочий источник не очищается; аварийный pair rollback сохраняет исходный журнал.
Архивы v9–17 проверяются и мигрируют перед очисткой. Старым executable не отдавать
новую БД, user_version вручную не понижать.

## T41c5b — история, detach и восстановление (tasks v19)

Журнал расширен occurrence_day и типами history/detach/root_save/root_restore/
root_delete/restore. Before/after допускают строгий OccurrenceRecord со стабильным
history_id(rule_id, day). Правка старого завершённого экземпляра сохраняет этот
ID, запланированный день и исходную completion date. Одинаковый DTO не дублируется.

При явном reopen прошлого экземпляра или назначении ему deadline membership
прошлой occurrence удаляется в той же транзакции. Он становится ordinary,
сохраняя root/child UUID, даты и связанные файлы/календарь/фокус. Активная серия
не меняется. Последующее завершение этого корня не превращает его обратно в
occurrence. Это opt-in путь: обычный режим и origin suppression не менялись.

`sync_regular_roots`: root_id, context_id FK binding, rule_id, day. Только
идентификаторы/день, без текста и FK на удаляемый root identity. Таблица сохраняет
происхождение после stop/detach/delete/purge. После остановки серии правки
обычной задачи идут в root_save, а не теряются из-за deferred. Root UUID после
purge нельзя создать снова обычным create: нужен явный trash restore.

| kind | Значение |
| --- | --- |
| history | OccurrenceRecord → OccurrenceRecord, тот же rule/day/root |
| detach | OccurrenceRecord → TaskRecord с прежним root UUID |
| root_save | TaskRecord → TaskRecord после stop/detach |
| root_restore | Явное восстановление дерева; after — TaskRecord либо OccurrenceRecord |
| root_delete | Только rule/day/root, оба тела null |
| restore | Явное восстановление поддерева текущего RegularRecord |

Restore отличается от простого добавления узла: будущий resolver должен учесть
барьер удаления. Восстановленный текущий корень остаётся обычной задачей без
запуска расписания; восстановленная завершённая прошлая occurrence остаётся
историей. Локальная корзина сохраняет прежние правила. Источник LocalData видит
физический detach membership, но не читает sync_regular_roots или журнал.

Migration v18→19 транзакционно пересоздаёт journal с расширенным CHECK и новым
nullable day, сохраняя seq/UUID/anchor/JSON bytes и frozen ordinary queue.
Lineage восстанавливается из имеющихся типизированных RegularRecord-снимков,
включая stop. Если старых фактов/метаданных недостаточно (например, единственный
v18 delete без прежнего снимка), происхождение не выдумывается: старый opaque
корень остаётся deferred до первоначального merge/preview. Старые payload не
переписываются на случайные day/rule. Более ранние схемы сразу получают v19.
DDL failure откатывает rename/таблицы/версию; старые архивы v9–18 поддержаны.
Публичные копии исключают новую lineage-таблицу, аварийный pair rollback оставляет
её в исходном профиле. Сохранённые локальные задачи/корзина/файлы не удаляются.

T41c5c1–c2a добавляют read-only history/current proposals,
см. SYNC_HISTORY_PLAN.md и SYNC_REGULAR_PLAN.md.
Это всё ещё факты, не подготовленные Operation. Общий барьер next_sync_sendable
остаётся; применение серверных tombstones/retention и выбор create/restore по
подтверждённому серверному состоянию — будущий resolver T41c5c. Наличие локального
history факта не разрешает вернуть retained/user_deleted тело без этого выбора.
Общий пояс аккаунта/transport/inbound/UI регистрации по-прежнему впереди.
