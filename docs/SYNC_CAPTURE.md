# Автоматическая локальная запись обычных задач — T41c4

Tasks v19, garden v7. `storage/sync_capture.py` включён в TaskStore.
Это подготовка исходящей очереди без HTTP, сервера, входа или применения inbound.
Обычный запуск, миграция и одна лишь UUID-привязка запись не включают.

## Явное включение

`configure_sync_task_capture(True, known_tasks)` требует существующую SyncBinding
и явно согласованный первоначальный состав UUID → состояние. Пустой словарь
допустим только для нового/проверенного пустого контекста; этот API сам не делает
первоначальный merge, подтверждение пользователя или авторизацию. Будущий UI
должен сначала выполнить backup/preview и выбор конфликтов. Секретов здесь нет.

Состояния `sync_task_presence`: live — участвующая задача; retained — тело убрано
политикой истории; deleted — явно удалена; deferred — тип ожидает отдельного
адаптера. Только UUID и состояние, без удалённого текста. Нет FK на identities:
служебная отметка переживает окончательную очистку локальной корзины.
`set_sync_task_presence` предназначен для будущего проверенного серверного
контекста, сам не подтверждает подлинность состояния. Применять метаданные и
соответствующие данные атомарно обязан будущий inbound adapter.

Флаг `sync_capture.enabled` хранится в SQLite. Выключение останавливает capture,
сохраняя существующие намерения и отметки. Это не команда отключения транспорта
или выхода из аккаунта. UI подключения и транспорта пока нет.

## Атомарные изменения

Общий `_write_task` записывает новое дерево/дату выполнения/событие сада и intent
в одной транзакции вызывающего API. Новая обычная задача → create; изменение или
выполнение → put; удаление дочерних UUID → prune с оставшимся деревом. Полное
удаление → delete без тела. Локальное восстановление из корзины → restore, а
для ещё не участвовавшего UUID → create. Одинаковая задача не создаёт новый put.
Следующее намерение зависит от последнего для того же task UUID; уже frozen
bytes не переписываются. Схема намерений/Receipt/base остаётся T41c1/T41c3.
Старый явный update_task_and_enqueue при включённом capture отклоняется,
чтобы не получить две записи одного изменения.

Редактирование названия старой retained-задачи или исключённой локальной
завершённой истории не возвращает её в облако. Явное повторное открытие даёт
restore/create соответственно. После explicit delete обычная правка не может
вернуть UUID; требуется восстановление из корзины. Ошибка подготовки intent
откатывает дерево, completion date, trash и garden event вместе с метаданными.

`suppress_sync_capture(origin)` — вложенный, exception-safe guard одного
TaskStore для incoming/profile_restore/bootstrap/regular. Он исключает обратную
запись и не заменяет транзакцию, серверную авторизацию или решение о наградах
сада. Локальный restore из корзины намеренно не подавляется. Другой TaskStore
продолжает записывать свои локальные изменения независимо.

## Границы этапа

T41c5c1 готовит только history proposals (SYNC_HISTORY_PLAN.md), без enqueue/
retirement и снятия общего барьера отправки.

T41c5a–b добавляют durable журнал current/history/rollover/stop/detach/restore
(SYNC_REGULAR_CAPTURE.md). Это ещё не отправляемые intents: наличие фактов
блокирует next_sync_sendable. Ниже граница обычного task capture T41c4.

Регулярные корни и их история помечаются deferred, включая создание следующего
слота и остановку серии. Они не сериализуются ошибочно как ordinary TaskRecord.
History/detach сохраняются отдельными facts T41c5b, их разрешение в сетевые
переходы типов — T41c5c.
Календарь/категории и их зависимости также впереди. Категория в task payload
не означает, что она уже подготовлена отдельным intent. AI-пути используют общий
write, но полный сценарий предложений отдельно этим этапом не заявляется.
До покрытия всех путей нельзя включать реальный transport или обещать полную
синхронизацию. Garden-награды за новые входящие выполнения ещё нужно согласовать.

## Миграция и копии

v16 → v17 создаёт только две пустые таблицы одной DDL-транзакцией. Неудача не
повышает версию и не оставляет часть схемы. Старые приложения могут отказать
читать новую БД — не понижать user_version вручную.
Публичные создаваемые/импортируемые копии после проверки очищают capture,
presence, outbox, intents и binding только в staged-копии и уплотняют SQLite.
Исходный профиль остаётся прежним. Аварийный rollback парного восстановления
сохраняет исходный флаг и отметки вместе с очередью. Архивы v9–16 поддержаны.
