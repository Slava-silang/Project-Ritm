# Архитектурная основа

Стек и пользовательское поведение согласованы в `SPEC.md`. В T01 реализованы точка входа и минимальное QML-окно. Приведённые ниже границы будущих модулей — исходное техническое предложение; модель данных, SQLite-хранилище, основные сценарии задач и их QML-интерфейс реализованы в T04–T09, включая фильтры и базовую корзину.

## Один процесс и локальная база

Первоначально — одно десктопное приложение, без собственного веб-сервера и облачного backend. SQLite хранит структурированные данные. Управляемые вложения лежат в отдельной папке; база хранит относительные идентификаторы и метаданные.

Предлагаемая структура после T01:

```text
src/ritm/
  __main__.py       # запуск
  domain/           # дерево задач, веса, прогресс, интервалы
  application/      # сценарии изменения данных, черновики ИИ
  storage/          # SQLite, миграции, файлы, резервные копии
  integrations/     # LLM и разбор выбранных материалов
  platform/         # ключи, трей, сон, автозапуск, окна
  ui/               # QObject-модели и связь с QML
  qml/              # представления и компоненты
  assets/           # изображения и подготовленные реплики
tests/
```

Создавать модули по мере появления поведения; пустые слои и обобщённую систему плагинов заранее не строить.

## Границы ответственности

### Domain и application

Правила дерева, выполнения, весов и недельного прогресса — Python без зависимости от Qt. Сценарий изменения проверяет входные данные и выполняется транзакционно. Завершение ветки, открытие предков и пересчёт прогресса должны представлять одно согласованное изменение.

Application предоставляет одни и те же операции для ручного интерфейса и подтверждённого черновика ИИ. Отдельных привилегированных путей записи для модели нет.

### QML и модели интерфейса

QML описывает отображение, тему, ввод и анимации. Python-модели сообщают об изменениях через механизмы Qt. Недельная полоса и карточки используют результаты одного расчёта; формулы в QML не дублируются.

### Фоновые операции

Сеть, извлечение текста, копирование больших файлов, резервные копии и упаковка не блокируют UI. Конкретный механизм фоновой работы выбрать в T01/T22 с учётом цикла событий Qt. Соединения SQLite использовать в пределах владеющего ими потока; управление транзакциями централизовать.

### Время

Хранить моменты времени с однозначной временной привязкой; отображать в местном часовом поясе. В расчётах сессий отдельно учитывать активные интервалы и паузы. Интервалы, пересекающие полночь/границу недели, распределять по фактическим частям, а не целиком по дню начала.

Текущие часы внедрять как заменяемую зависимость для тестов. Сон, блокировка экрана и восстановление после сбоя обрабатывать разными событиями.

### Хранение и восстановление

Пользовательский профиль определяется средствами Qt, отдельно от исходников и исполняемого файла. Тестовый профиль явно задаётся отдельно. Настройки, база, вложения, история и копии имеют понятные границы; API-ключ в файловый профиль не попадает.

Миграции имеют версии. Копию SQLite получать согласованным способом, учитывая WAL; простого копирования открытого файла недостаточно. База и вложения копируются как единый восстанавливаемый набор. Перед заменой рабочего профиля копия проверяется; неудачное восстановление сохраняет предыдущий рабочий набор. Данные между обновлениями программы сохраняются.

### Адаптер LLM

Первый адаптер — для выбранной модели из SPEC. Перед реализацией проверить актуальные официальные API-документы. Параметры модели настраиваются; секрет передаётся отдельно от сообщений.

Адаптер получает явный контекст и возвращает результат для валидации. Черновик имеет идентификатор; применение идемпотентно. Отмена запроса и поздний ответ не должны приводить к скрытой записи. Изменившаяся задача требует повторной проверки актуальности черновика.

Автотесты используют подменный провайдер: корректный результат, ошибка, задержка, отмена, повреждённый ответ. Реальный платный запрос — отдельная согласованная проверка.

### Платформенные возможности

Отдельные адаптеры: защищённое хранилище, сон/блокировка, автозапуск, трей и особенности окна компаньона. Возможность определяется фактически; неподдерживаемое поведение отражается явно.

Основной текущий стенд: Linux Mint 22.3, x86_64, Cinnamon/X11. Windows и Wayland не считать проверенными по результатам X11.

## Запуск и упаковка

Разработка — CPython в окружении uv. QML и ресурсы включаются в пакет проекта, а путь к ним определяется относительно ресурсов пакета, без зависимости от текущего каталога.

Первый кандидат упаковки — `pyside6-deploy` с Nuitka в явно заданном режиме standalone. Он формирует исполняемый файл и набор необходимых библиотек, включая среду Python. Это отдельный шаг от `uv build`, создающего Python-дистрибутив.

Упаковывать и проверять минимальный интерфейс в начале разработки. Затем повторять упаковку при добавлении влияющих на неё зависимостей и перед выпуском. Подробности — `DEVELOPMENT.md`.

## Журнал технических решений

### T17a — библиотека материалов

SQLite v8 хранит независимые файлы в materials и связи с владельцами в material_links. Составной ключ не допускает повторную ссылку на тот же материал в одном узле. Проверка живого владельца и запись выполняются в одной транзакции. Ссылки скрываются вместе с узлом и возвращаются при восстановлении. При очистке задачи удаляется связь, общая копия остаётся в библиотеке.

Копирование использует существующий каталог attachments и UUID файла. Библиотека и все ссылки открывают один и тот же сохранённый путь. При резервном копировании T19 обе таблицы и файлы входят в профиль.

### T17 — управляемые вложения

SQLite v7 хранит UUID вложения, владельца, исходное имя, расширение и размер. Корень ссылается на task_identities, а узел проверяется по активному дереву в транзакции. Метаданные переживают пересохранение и восстановление дерева. Список и открытие скрывают записи узлов в корзине.

storage/attachments.py копирует обычный файл блоками в отдельную папку UUID внутри профиля. Скопированный файл записывается до транзакции метаданных. При обработанной ошибке новая копия убирается. Принудительное завершение до транзакции может оставить файл без метаданных. QDesktopServices получает проверенный локальный путь на потоке интерфейса.

### T16 — недельная статистика

domain/statistics.py рассчитывает средний прогресс по локальным датам дедлайнов и обрезает закрытые рабочие интервалы по границам выбранной недели. Разбиение по местным дням использует логику T14. Снимок для StatisticsPane.qml готовится в фоновом потоке. Текущий счётчик просроченных обновляется по часам независимо от выбранной недели.

SQLite v6 связывает дату завершения с постоянным ID задачи. Дата записывается атомарно при завершении, сбрасывается при возвращении в работу и сохраняется при переносе корня в корзину и восстановлении. Миграция оставляет исторические даты неизвестными.

### T15 — сон, блокировка и выход

Адаптер Linux получает PrepareForSleep через системную шину и ActiveChanged Cinnamon через шину сессии. При работающем таймере запрашивается асинхронный delay inhibitor logind. После попытки записи паузы дескриптор освобождается. Очередь контроллера сохраняет время прихода события, включая случай занятой базы. Разблокировка и пробуждение сессию не возобновляют. [Интерфейс logind](https://freedesktop.org/software/systemd/man/latest/org.freedesktop.login1.html).

Окно закрывается после подтверждения и успешной записи завершения. SIGINT/SIGTERM сохраняют возможность остановить процесс из терминала, а незавершённая сессия при следующем старте попадает в сценарий T14.

### T14 — восстановление и правка истории

На первом успешном чтении профиля открытая сессия переходит в режим проверки. Указанное окончание должно быть между последней сохранённой отметкой и текущим временем. Вариант по последней отметке закрывает текущий интервал по его началу или завершает сессию на последней паузе. Команда сверяет ревизию перед изменением.

Ручная запись хранится как закрытая сессия с одним интервалом. При уменьшении длительности обрезается конец рабочих интервалов, при увеличении удлиняется последний. UTC-границы позволяют разбивать интервалы по локальным суткам без начисления пауз. Схема SQLite остаётся v5.

### T13 — фокус-сессии

В схеме v5 focus_sessions ссылается на постоянный реестр task_identities, а focus_intervals хранит упорядоченные интервалы фактической работы в UTC-микросекундах. Пауза закрывает интервал, продолжение открывает следующий. Частичные уникальные индексы разрешают одну незавершённую сессию и один открытый интервал на сессию. Смена сессии одной транзакцией завершает прежнюю и открывает новую. Под блокировкой записи сверяются ID и ревизия активной сессии.

TaskController получает снимок и историю в фоновом потоке. Обновление отсчёта раз в секунду работает с этим снимком без обращений к базе. Проверяемые часы передаются в контроллер. Хранение интервалов позволяет позднее распределить время по местным дням и восстановить незавершённую сессию.

### T12a — события без задач

WorkBlock представляет блок задачи (task_id задан, title пустой) либо самостоятельное событие (task_id=None, непустой title). Доменные и SQL-проверки защищают оба варианта. Событие не создаёт фиктивную задачу. Общие UTC-интервалы, пересечения, перенос и изменение размера применяются к обоим; дедлайн и planned_time относятся только к владельцу-задаче.

Схема v4 добавляет title и разрешает NULL task_id в work_blocks. Миграция v1–v3 создаёт новую таблицу, копирует прежние записи, заменяет таблицу и индексы в одной транзакции. LEFT JOIN при чтении возвращает самостоятельные события всегда, а блоки задач — только для живых корней. Реестр и скрытые архивные блоки сохраняются.

Проекция UI передаёт kind=event, isEvent и eventTitle; события показаны фиолетовым. Форма меняет название и интервал, тип/владелец существующей записи неизменны. Защита expected учитывает также название, в хранилище сравнивается полный исходный объект под блокировкой записи. T25 должен учитывать события как занятые интервалы.

### T12 — жесты и защищённое изменение

DayTimeline.qml отображает часы по прошедшему UTC-времени от локальной полуночи: 23/25 часов в дни DST, отдельные подписи одинаковых часов со смещением. Данные шкалы/полосы пересечений формируются в ui/calendar.py. Минимальная визуальная высота короткого блока учитывается при раскладке полос, не меняя длительность и условия конфликтов. Передняя/конечная части ночного блока получают разные разрешения ручек.

CalendarPane использует Drag/DropArea для переноса между днями; отдельный ghost в Overlay хранит снимок источника. При достижении края viewport включается прокрутка. На шкале MouseArea обрабатывает захват с preventStealing, переводит смещение указателя в кратные 15 минут и показывает локальный предпросмотр. Успешный ответ заменяет снимок; ошибка снимает предпросмотр через stateChanged, Escape не отправляет команду. Форма редактирования использует тот же блок, блокируя смену задачи.

change_block в Python выполняет UTC-сдвиг/изменение конца или перенос по локальным дням с сохранением длительности/точности. При неоднозначном дне предпочтительно исходное смещение, при несуществующем времени — отказ. Параметр sourceDay позволяет корректно переносить продолжение ночного блока. Изменения неизменённых полей формы сохраняют исходные секунды/микросекунды.

TaskController проверяет начало/конец из переданного снимка. CalendarService.update_block передаёт expected в TaskStore, где повторное сравнение делается после BEGIN IMMEDIATE; гонка не перезаписывает новый интервал. ID/владелец неизменны, ошибки откатываются. Предупреждения пересчитываются на подтверждённом снимке и не запрещают запись. Схема v3 не меняется.

### T11 — календарный UI

CalendarPane.qml — отдельный компонент недели/месяца и формы блока, Main.qml переключает вкладки и открывает карточку выбранного события. ui/calendar.py формирует локальные периоды и снимки без Qt/БД: полные недели с понедельника, выбор дня, отдельные отметки сроков, дневные части интервалов и форматирование длительностей. Месяц включает соседние дни; узкий недельный вид использует компактные счётчики и подробную повестку выбранного дня.

TaskController сохраняет календарную конфигурацию (mode/anchor/day), отдельный calendarChanged и сообщение результата команды. Навигация, создание и загрузка снимков идут в существующем executor; SQLite и CalendarService используются в том же рабочем потоке. Суммы планового времени включены в снимки карточек. Таймер обновляет текущую дату после полуночи, не перемещая пользователя в другой период. Форма валидирует локальные моменты и достижимость периода до записи; предупреждения допускают сохранение. Окончательная проекция после успешной команды обновляет оба представления.

Блоки хранятся в UTC, дневные сегменты вычисляются по локальным границам суток. Полночь может иметь другое смещение следующего дня; день DST не предполагается равным 24 часам. Повторяющийся час без явного смещения отвергается, несуществующий местный час тоже. Каждый сегмент ссылается на исходный блок, общий planned_duration не суммирует сегменты повторно. Дедлайн не создаёт WorkBlock.

Новый CalendarPane.qml включён в pysidedeploy.spec и wheel. Запуск извлечённого wheel отдельно от репозитория проверяет относительное разрешение обоих QML-файлов; пересборка standalone относится к проверке выпуска. T12 добавит мышиные операции, не меняя правила расчёта календаря.

### T10 — интервалы календаря и постоянная идентичность главной задачи

`domain/calendar.py` не зависит от Qt: WorkBlock неизменяем и хранит канонические UTC-даты с положительной длительностью. Начальные локальные даты проверяются обратным преобразованием через UTC, чтобы отвергать несуществующий час DST. Повторяющиеся часы задаются однозначным смещением/fold; длительность считается между UTC-моментами. SQLite использует целые микросекунды относительно 1970-01-01, без float timestamp. Полуоткрытые интервалы и политика сумм/предупреждений описаны в S05.

CalendarService использует тот же TaskStore. Создание и изменение блока берут BEGIN IMMEDIATE, проверяют живую главную задачу, записывают интервал и читают согласованный контекст задачи/пересекающихся блоков до commit. Чистый block_warnings оценивает этот снимок; предупреждения не отменяют запись. Повторная оценка существующего блока читает задачу и соседей в одной read-транзакции. Изменение сохраняет ID и task_id. list_work_blocks фильтрует по владельцу и/или пересечению с полуоткрытым диапазоном, упорядочивает по starts_us/id. Пересечения с другими задачами тоже учитываются; суммы берутся только для выбранного владельца.

Схема v3: task_identities(id) — постоянный реестр главных задач, work_blocks(id,task_id,starts_us,ends_us) — календарные интервалы. При миграции v1/v2 реестр получает ID живых корней и владельцев записей корзины. Новые/восстановленные корни регистрируются при _write_task. create_task запрещает повторное использование зарегистрированного ID, включая архивный, чтобы другой задаче не достались чужие блоки. Даты защищены SQL-проверками типа/диапазона и положительной длительности.

FK work_blocks ссылается на task_identities, а не на nodes. Удаление корня в T09 сохраняет реестр/блоки; JOIN к nodes с kind=0 скрывает архивные блоки. Восстановление корня делает прежние блоки видимыми автоматически, без изменения старого JSON-формата корзины. Удаление подзадачи не затрагивает интервалы владельца. Финальная очистка T18 должна сначала удалить управляемые связанные данные, затем освободить идентичность; обычное редактирование/корзина этого не делают.

T11 подключает CalendarService к фоновым командам и создаёт локальное отображение недели/месяца. В UI не дублировать UTC-арифметику, суммы и условия предупреждений. Дедлайн остаётся отдельным полем Task и отдельной календарной отметкой; окончание блока не меняет выполнение.

### T09 — навигация и базовая корзина

`domain/task_list.py` — чистая проекция: фильтры, поиск по текстам дерева, группы и сортировка по UTC-моменту срока. now передаётся явно; равенство срока не является просрочкой. TaskController хранит исходные Task и снимки, фильтрует без БД; QTimer раз в секунду проверяет границы и уведомляет список только при изменении результата. Сигналы списка, выбранной карточки, категорий и состояния разделены, чтобы обновление часов не уничтожало ввод в форме. Фильтры меняют выбор на подходящий; после мутации карточка может остаться вне фильтра с подписью. Узкая компоновка показывает список или карточку.

Категории уже существуют в v1. Новая категория и создание/изменение задачи теперь записываются одним соединением и транзакцией. Фильтр использует ID категории; форма передаёт выбранный ID и текст. При совпадении текста сохраняется выбранный ID (в том числе при одинаковых названиях), иначе ввод повторно использует совпадение без учёта регистра либо создаёт новую категорию. Отдельное переименование/удаление категорий пока не реализовано.

Схема v2 добавляет отдельную trash, не меняя таблицы nodes/categories. v1→v2 выполняется под BEGIN IMMEDIATE; DDL и номер версии откатываются вместе при ошибке. Новая база создаёт обе части сразу. Неизвестная версия/подпись по-прежнему не изменяется.

storage/codec.py кодирует версионированный снимок Task: ID/Decimal/aware datetime — текст, длительность — целые микросекунды. Корзина хранит снимки всего дерева до и после удаления, выбранный node_id, уровень и UTC-время удаления. Активный nodes содержит только живую часть дерева; перенос в корзину, пересчёт выполнения/весов и запись активного дерева атомарны. Это позволяет существующему _write_task заменять активные потомки, не затрагивая отдельно удалённые ветки.

completion.remove_node/restore_node — правила удаления/восстановления. Главная задача восстанавливается целиком, отдельная ветка объединяется с актуальным деревом, сохраняя новые изменения соседей и метаданных. Если оставшиеся ID/веса совпадают со снимком после удаления, возвращаются исходные веса; иначе действует автоматическое добавление по S03. Повторяющиеся ID не допускаются; коллизия откатывает восстановление и сохраняет архив. Отдельно удалённый родитель должен быть восстановлен раньше потомка.

В T09 ID удалённого узла остаётся в JSON, а не в активном nodes. С T10 для главных задач есть постоянный реестр и сохраняющиеся календарные интервалы. С T13/T17 нельзя добавлять FK ON DELETE CASCADE к удаляемым nodes для таймерных/файловых данных без расширения сценариев корзины: связи должны переживать перенос и восстановление. T18 завершает сохранность всего связанного набора и явную очистку; базовая корзина T09 не означает готовность этого этапа.

### T08 — интерфейс и фоновые команды

TaskController (ui/tasks.py) передаёт QML простые снимки QVariantList/QVariantMap и отдельные сигналы изменения данных/состояния. Операции последовательно выполняются в ThreadPoolExecutor с одним потоком: каждый вызов открывает свой TaskStore в этом же потоке. Qt-объекты и представления обновляются только после доставки queued Signal в главный поток. На время команды повторный ввод отключён; подтверждённый снимок меняется после успешной записи. При ошибке форма и введённые данные остаются. Длительные будущие интеграции не должны занимать эту очередь хранения.

QML получает backend через required initial property, формулы не дублируются. Создание, основные поля, переименование, выполнение, веса проходят через TaskService. edit_details меняет только метаданные текущего дерева внутри транзакции; UUID/дети/категория сохраняются. create_task берёт блокировку до проверки ID и не допускает перезапись. Все None-веса при создании инициализируются. Наивный ввод срока интерпретируется в местном поясе; неизменённые отображаемые время/срок сохраняют исходную точность и смещение.

Профиль выбирается после настройки имени Qt-приложения: QStandardPaths.AppDataLocation/tasks.sqlite3. --profile явно отделяет тестовый набор; --smoke-test без этого флага создаёт TemporaryDirectory. На завершении executor закрывается до уничтожения backend, QML-движок освобождается раньше контроллера. SIGINT/SIGTERM доставляют quit через Qt, heartbeat обеспечивает обработку Python-сигналов.

Main.qml использует светлую палитру и явный фон диалогов, чтобы системная тёмная тема не делала подписи нечитаемыми. Текст пользователя отображается без интерпретации HTML. В T09 добавлены узкая компоновка, фильтры, категории и удаление/восстановление дерева; расширение корзины на вложения и связанные данные остаётся T18.

### T07 — веса и прогресс

`domain/weights.py`: equal_weights, set_weights, initialize_weights, progress. Расчёт распределения выполняется через Fraction и целые сотые процента; результат — Decimal. Это исключает зависимость от глобального Decimal context. Метод наибольших остатков сохраняет сумму 100%; равные остатки разрешаются порядком соседей. Ручной набор валидируется целиком по UUID; неверная сумма не нормализуется молча. Политика нулей, добавления и удаления записана в S03.

completion.add_subtask/remove_subtask объединяют структурное изменение, веса и пересчёт выполнения. TaskService сохраняет результат одной транзакцией; операции выполнения и добавления нижнего пункта инициализируют незаданные веса. Схема SQLite v1 не меняется. Исходные модели и низкоуровневый roundtrip допускают None/произвольный Decimal; прикладные операции требуют полного набора с суммой 100% либо всех None. Создание задачи через TaskService инициализирует веса перед сохранением.

Прогресс вычисляется из дерева, отдельное поле в базе не хранится; QML должен использовать один Python-расчёт. Выполнение и прогресс различаются при нулевых весах: завершение определяется всеми ветками. Интерфейс T08 должен показывать статус по completed. Удаление ветки пока доступно только как программный сценарий; будущая корзина T18 должна обеспечить восстановление и связанных данных.

### T06 — сценарии выполнения

`domain/completion.py` возвращает новое дерево: set_completed каскадно меняет выбранную ветку, add_subtask/add_item добавляют потомка, затем выполнение пересчитывается снизу вверх. Для непустой ветки используется all по непосредственным детям; у листьев и пустой главной задачи остаётся ручная отметка. Пустой список не завершает задачу автоматически. Соседние отметки сохраняются. Данные модели сами не запускают сценарии; при изменении из UI/ИИ следует использовать application.TaskService.

TaskService обращается к TaskStore.update_task: BEGIN IMMEDIATE до чтения актуального дерева, чистое преобразование, проверка сохранения ID главной задачи, запись дерева, commit. Исключение откатывает всё. Callback не обращается к соединению; вложенные операции хранилища не допускаются. Низкоуровневый save_task остаётся для первоначального сохранения/восстановления данных; правила выполнения сосредоточены в domain. С T07 добавление/удаление первого уровня также перераспределяет веса.

### T05 — первая схема SQLite

TaskStore принимает явный путь, владеет соединением в одном потоке и не зависит от Qt. Выбор пользовательского профиля будет в T08. Новая пустая база получает application_id RITM и user_version 1 одной транзакцией. Неизвестная схема или чужая непустая база отклоняется; будущие миграции добавляются явно.

Таблица categories хранит категории; nodes хранит три уровня с UUID, parent_id и порядком среди соседей. Внешние ключи включены, ограничения и триггеры защищают уровни. Обновление задачи сохраняет её ID и атомарно заменяет собственных потомков, сохраняя переданные ID. Коллизия с другим деревом откатывает всё изменение. API удаления пока отсутствует; корзина относится к T18.

Decimal хранится текстом без потери точности; положительная timedelta — целым числом микросекунд (ограничена signed 64-bit); aware datetime — ISO 8601 со смещением. Чтение дерева выполняется одним рекурсивным запросом; чтение списка — в одной read-транзакции. При загрузке данные снова проходят валидацию доменной модели.

### T04 — модель данных

Task содержит только Subtask первого уровня, те — только конечные ChecklistItem (проверяется точный тип). Category существует отдельно; Task хранит необязательный category_id. Неизменяемые dataclasses и tuples защищают модель от обхода валидации обычным присваиванием. При редактировании dataclasses.replace сохраняет UUID. SQLite-адаптер в T05 должен восстанавливать эти же ID, datetime с часовым поясом, timedelta и Decimal, а не создавать новые идентификаторы.

Сложность и ожидаемая длительность доступны только Task. Отсутствие длительности — None; указанная длительность положительна. Вес первого уровня в исходных данных может быть None; его инициализация, валидация суммы и прогресс реализованы в T07. Отметки выполнения являются данными; каскадные переходы реализованы сценариями T06. Модели не импортируют Qt и не выполняют ввод-вывод.

### T03 — технический стенд окна компаньона

Qt.Tool + FramelessWindowHint + WindowStaysOnTopHint, прозрачный фон и маска QRegion работают на Cinnamon/X11. Маска исключает прозрачный фон из обработки кликов. Ручное перемещение работает; состояние активного полноэкранного окна доступно через EWMH/xprop, скрытие и возврат проверены на собственном окне.

Отдельный `scripts/companion_probe.py` использует QtWidgets только как минимальный платформенный стенд, без сохранения данных и подключения к реальному приложению. Будущий интерфейс остаётся QML; применение маски к QtQuick-окну нужно проверить в T28. Синхронный опрос xprop в прототипе не переносить в production: потребуется неблокирующий платформенный адаптер. При сборке приложения исключать scripts из анализа модулей, чтобы технический стенд не расширял runtime-зависимости. Временный круглый персонаж не является выбранным дизайном.

### T01 — 8 ноября 2026

- Python 3.12 выбран по уже установленной и проверенной версии. PySide6 6.12.0 и инструменты фиксируются в `uv.lock`. На этом этапе поддерживается Python 3.12; расширение диапазона требует проверки.

### T02 — самостоятельная упаковка

- `src/main.py` — тонкий вход для deploy; рабочее приложение остаётся в пакете `ritm`. Это сохраняет совпадение путей QML при обычном и скомпилированном запуске.
- Исходная `pysidedeploy.spec` использует относительные пути. `scripts/build_linux.py` передаёт инструменту временную рабочую копию и устанавливает standalone-режим. Пакетами управляет uv через группу packaging, а не автоматическая установка pip из deploy.
- Версия приложения перенесена в `ritm.__version__`; метаданные Hatchling читаются оттуда. Так runtime не требует editable-метаданных, неправильно сопоставлявшихся Nuitka с именем Python-модуля.
- Nuitka 4.1.1: минимальный воспроизводимый дефект — перенести ту же поставку в кириллическую папку и вызвать `--version`; ASCII-путь с пробелами работает, кириллица вызывает SIGABRT до Python-кода. GDB подтвердил ранний abort. Для исправления выбран Nuitka 4.2.2, где Linux-конвертация путей учитывает locale и UTF-8 fallback. Проверка — `check_linux_build.py --relocation-only`, работающая с настоящей поставкой, а не макетом.
- Контейнерная проверка монтирует только поставку, без исходников и `.venv`, и проверяет отсутствие команды Python. Системные runtime-зависимости зафиксированы Dockerfile на Ubuntu 24.04. Реальный оконный backend проверяется на хосте отдельно.
- Standalone поставляется папкой; tar.gz и SHA256 создаются после сборки. Наличие Python wheel не считается выполнением T02.
