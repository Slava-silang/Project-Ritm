# Архитектурная основа

Стек и пользовательское поведение согласованы в `SPEC.md`. В T01 реализованы точка входа и минимальное QML-окно. Приведённые ниже границы будущих модулей — исходное техническое предложение; бизнес-функции ещё не реализованы.

## Один процесс и локальная база

Первоначально — одно десктопное приложение, без собственного веб-сервера и облачного backend. SQLite хранит структурированные данные. Управляемые вложения лежат в отдельной папке; база хранит относительные идентификаторы и метаданные.

Предлагаемая структура после T01:

```text
src/ritm/
  __main__.py       # запуск
  domain/           # дерево задач, веса, прогресс, интервалы
  application/      # сценарии изменения данных, черновики ИИ
  storage/          # SQLite, миграции, файлы, резервные копии
  integrations/     # LLM и разбор выбранных материалов
  platform/         # ключи, трей, сон, автозапуск, окна
  ui/               # QObject-модели и связь с QML
  qml/              # представления и компоненты
  assets/           # изображения и подготовленные реплики
tests/
```

Создавать модули по мере появления поведения; пустые слои и обобщённую систему плагинов заранее не строить.

## Границы ответственности

### Domain и application

Правила дерева, выполнения, весов и недельного прогресса — Python без зависимости от Qt. Сценарий изменения проверяет входные данные и выполняется транзакционно. Завершение ветки, открытие предков и пересчёт прогресса должны представлять одно согласованное изменение.

Application предоставляет одни и те же операции для ручного интерфейса и подтверждённого черновика ИИ. Отдельных привилегированных путей записи для модели нет.

### QML и модели интерфейса

QML описывает отображение, тему, ввод и анимации. Python-модели сообщают об изменениях через механизмы Qt. Недельная полоса и карточки используют результаты одного расчёта; формулы в QML не дублируются.

### Фоновые операции

Сеть, извлечение текста, копирование больших файлов, резервные копии и упаковка не блокируют UI. Конкретный механизм фоновой работы выбрать в T01/T22 с учётом цикла событий Qt. Соединения SQLite использовать в пределах владеющего ими потока; управление транзакциями централизовать.

### Время

Хранить моменты времени с однозначной временной привязкой; отображать в местном часовом поясе. В расчётах сессий отдельно учитывать активные интервалы и паузы. Интервалы, пересекающие полночь/границу недели, распределять по фактическим частям, а не целиком по дню начала.

Текущие часы внедрять как заменяемую зависимость для тестов. Сон, блокировка экрана и восстановление после сбоя обрабатывать разными событиями.

### Хранение и восстановление

Пользовательский профиль определяется средствами Qt, отдельно от исходников и исполняемого файла. Тестовый профиль явно задаётся отдельно. Настройки, база, вложения, история и копии имеют понятные границы; API-ключ в файловый профиль не попадает.

Миграции имеют версии. Копию SQLite получать согласованным способом, учитывая WAL; простого копирования открытого файла недостаточно. База и вложения копируются как единый восстанавливаемый набор. Перед заменой рабочего профиля копия проверяется; неудачное восстановление сохраняет предыдущий рабочий набор. Данные между обновлениями программы сохраняются.

### Адаптер LLM

Первый адаптер — для выбранной модели из SPEC. Перед реализацией проверить актуальные официальные API-документы. Параметры модели настраиваются; секрет передаётся отдельно от сообщений.

Адаптер получает явный контекст и возвращает результат для валидации. Черновик имеет идентификатор; применение идемпотентно. Отмена запроса и поздний ответ не должны приводить к скрытой записи. Изменившаяся задача требует повторной проверки актуальности черновика.

Автотесты используют подменный провайдер: корректный результат, ошибка, задержка, отмена, повреждённый ответ. Реальный платный запрос — отдельная согласованная проверка.

### Платформенные возможности

Отдельные адаптеры: защищённое хранилище, сон/блокировка, автозапуск, трей и особенности окна компаньона. Возможность определяется фактически; неподдерживаемое поведение отражается явно.

Основной текущий стенд: Linux Mint 22.3, x86_64, Cinnamon/X11. Windows и Wayland не считать проверенными по результатам X11.

## Запуск и упаковка

Разработка — CPython в окружении uv. QML и ресурсы включаются в пакет проекта, а путь к ним определяется относительно ресурсов пакета, без зависимости от текущего каталога.

Первый кандидат упаковки — `pyside6-deploy` с Nuitka в явно заданном режиме standalone. Он формирует исполняемый файл и набор необходимых библиотек, включая среду Python. Это отдельный шаг от `uv build`, создающего Python-дистрибутив.

Упаковывать и проверять минимальный интерфейс в начале разработки. Затем повторять упаковку при добавлении влияющих на неё зависимостей и перед выпуском. Подробности — `DEVELOPMENT.md`.

## Журнал технических решений

### T04 — модель данных

Task содержит только Subtask первого уровня, те — только конечные ChecklistItem (проверяется точный тип). Category существует отдельно; Task хранит необязательный category_id. Неизменяемые dataclasses и tuples защищают модель от обхода валидации обычным присваиванием. При редактировании dataclasses.replace сохраняет UUID. SQLite-адаптер в T05 должен восстанавливать эти же ID, datetime с часовым поясом, timedelta и Decimal, а не создавать новые идентификаторы.

Сложность и ожидаемая длительность доступны только Task. Отсутствие длительности — None; указанная длительность положительна. Вес первого уровня пока может быть None; суммирование и автоматическое распределение относятся к T07. Отметки выполнения являются данными, каскадные переходы будут сценариями T06. Модели не импортируют Qt и не выполняют ввод-вывод.

### T03 — технический стенд окна компаньона

Qt.Tool + FramelessWindowHint + WindowStaysOnTopHint, прозрачный фон и маска QRegion работают на Cinnamon/X11. Маска исключает прозрачный фон из обработки кликов. Ручное перемещение работает; состояние активного полноэкранного окна доступно через EWMH/xprop, скрытие и возврат проверены на собственном окне.

Отдельный `scripts/companion_probe.py` использует QtWidgets только как минимальный платформенный стенд, без сохранения данных и подключения к реальному приложению. Будущий интерфейс остаётся QML; применение маски к QtQuick-окну нужно проверить в T28. Синхронный опрос xprop в прототипе не переносить в production: потребуется неблокирующий платформенный адаптер. При сборке приложения исключать scripts из анализа модулей, чтобы технический стенд не расширял runtime-зависимости. Временный круглый персонаж не является выбранным дизайном.

После эксперимента записывать здесь: решение, причину, отвергнутый вариант при существенном компромиссе, проверенный стенд и связанные задачи.

### T01 — 8 ноября 2026

- Python 3.12 выбран по уже установленной и проверенной версии. PySide6 6.12.0 и инструменты фиксируются в `uv.lock`. На этом этапе поддерживается Python 3.12; расширение диапазона требует проверки.
- Hatchling собирает Python-пакет из `src/ritm`, включая QML. GUI-точка входа `ritm` и модуль `python -m ritm` используют один `main()`.
- `app.py` загружает Main.qml относительно установленного модуля. Текущий каталог не влияет на поиск ресурса; проверены отдельная папка и wheel с включённым QML.
- Стиль Qt Quick Controls — Basic, чтобы первая проверка не зависела от системного плагина оформления. Цвета стартового окна временные; полноценные темы относятся к T20.
- `--smoke-test` закрывает окно через 800 мс; это диагностика запуска. Тесты идут offscreen, реальный X11 проверен отдельно. Qt-события обслуживаются стандартным циклом QGuiApplication; фоновых операций в T01 ещё нет.
- База, пользовательские файлы, API и системный трей пока не создаются. Окно T01 закрывается полностью; будущее поведение трея относится к T21.

### T02 — самостоятельная упаковка

- `src/main.py` — тонкий вход для deploy; рабочее приложение остаётся в пакете `ritm`. Это сохраняет совпадение путей QML при обычном и скомпилированном запуске.
- Исходная `pysidedeploy.spec` использует относительные пути. `scripts/build_linux.py` передаёт инструменту временную рабочую копию и устанавливает standalone-режим. Пакетами управляет uv через группу packaging, а не автоматическая установка pip из deploy.
- Версия приложения перенесена в `ritm.__version__`; метаданные Hatchling читаются оттуда. Так runtime не требует editable-метаданных, неправильно сопоставлявшихся Nuitka с именем Python-модуля.
- Nuitka 4.1.1: минимальный воспроизводимый дефект — перенести ту же поставку в кириллическую папку и вызвать `--version`; ASCII-путь с пробелами работает, кириллица вызывает SIGABRT до Python-кода. GDB подтвердил ранний abort. Для исправления выбран Nuitka 4.2.2, где Linux-конвертация путей учитывает locale и UTF-8 fallback. Проверка — `check_linux_build.py --relocation-only`, работающая с настоящей поставкой, а не макетом.
- Контейнерная проверка монтирует только поставку, без исходников и `.venv`, и проверяет отсутствие команды Python. Системные runtime-зависимости зафиксированы Dockerfile на Ubuntu 24.04. Реальный оконный backend проверяется на хосте отдельно.
- Standalone поставляется папкой; tar.gz и SHA256 создаются после сборки. Наличие Python wheel не считается выполнением T02.
