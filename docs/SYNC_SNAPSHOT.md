# Постоянное облачное состояние desktop

Tasks schema v21 добавляет только `sync_remote_snapshot`: один bounded full
snapshot для текущего binding. Данные представлены каноническими wire pages,
при записи и чтении проходят SnapshotCollector (полнота, UUID, ссылки, лимиты,
версии/даты/типы). Частичные страницы не выдаются и не сохраняются как полный
снимок. При отсутствии cache API возвращает None — неизвестность, а не приказ
очистить профиль и не доказательство отсутствия конкретной задачи.

`remember_sync_snapshot(snapshot)` сохраняет сведения, полученные будущим
аутентифицированным транспортом. Серверное поколение должно совпадать с binding.
Watermark не уменьшается; при одинаковом watermark разрешены новый snapshot_id
и иной порядок тех же записей, но не иное содержимое. В более новом снимке для
сохранившейся сущности revision/epoch не уменьшаются; одна entity revision не
содержит разные тела/epochs. Возврат live сущности после marker требует нового
epoch. Полный снимок может не содержать сущность из прежнего снимка вследствие
облачной retention; это не удаляет локальные данные.

`save_sync_receipt_and_snapshot(receipt, snapshot)` сохраняет applied receipt,
UUID mappings/phase acknowledgements и полный снимок одной BEGIN IMMEDIATE
транзакцией. Снимок должен покрывать receipt.revision. Ошибка записи, неизвестная
привязка, неверная квитанция, противоречие/старый watermark откатывают всё.
Повтор прежнего receipt остаётся идемпотентным. Rejected receipt отдельно
поддерживает прежний save_sync_receipt; он не выдаёт подтверждение applied.

Снимок может быть новее операции: её результат мог уже измениться с другого
устройства или попасть под retention. Поэтому подтверждённый запрос не обязан
буквально присутствовать в более новом снимке. Receipt доказывает приём конкретных
bytes/op_id, full snapshot сообщает актуальное состояние. Здесь нет локального
выдумывания «серверных эффектов» из отправленного payload. Проверка источника/
владельца HTTPS-соединения относится к будущему transport; эти storage API сами
не выполняют сетевые запросы и не дают полномочий произвольным внешним данным.

`read_sync_snapshot()` восстанавливает полное состояние после reopen. Последующая
подготовка может использовать его actual revision/epoch вместо ручных тестовых
оснований. Автоматическая сборка context/queue step и settled retirement описаны в
SYNC_PREPARE_LOOP.md; первый блок ещё требует покрытия оставшихся переходов. Эти API не меняют nodes/trash/files,
не снимают общий send barrier и не являются inbound merge/начислением сада.

Миграция v20→21 создаёт пустой cache, сохраняя intents/frozen bytes/facts/ledger.
Публичный backup/import удаляет cache в staged-копии перед binding; исходный
профиль не очищается. Архивы v9–20 принимаются и мигрируют штатно. Внутренний
аварийный rollback сохраняет данные. Garden schema v7 и зависимости прежние.
