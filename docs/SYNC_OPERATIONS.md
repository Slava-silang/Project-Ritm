# Операции и квитанции v1 — T41b2b1

Реализован чистый `integrations/sync_operations.py`, не сеть/сервер/outbox.
Формат сущностей — [SYNC_ENTITIES.md](SYNC_ENTITIES.md), общая схема —

## Запрос

Оболочка ровно `version: 1`, `kind: operation`, `data`.

| Поле data | Значение |
| --- | --- |
| op_id | Постоянный UUID операции, повтор не меняет его |
| device_id | UUID явно подключённого устройства |
| server_id | UUID поколения сервера, не адрес/токен |
| target_kind | task, category, block, regular, occurrence или calendar_settings |
| target_id | UUID корня/категории/блока/правила |
| base_revision | Неотрицательная ревизия строкой |
| delete_epoch | Неотрицательный барьер удаления строкой |
| action | create, put, restore, delete, prune, stop_regular, rollover |
| payload | Полная оболочка сущности либо null по действию |

Счётчики — канонические ASCII-строки 0…2^63−1. UUID канонические.
create требует base_revision=0/delete_epoch=0, остальные — base_revision>0.
kind и ID payload совпадают с целью. Клиент не передаёт RemovalRecord вместо
команды: серверные ревизии отметок удаления не назначаются клиентом.

| Действие | payload и правило границы |
| --- | --- |
| create/put/restore | Сущность соответствующего типа |
| delete | Только null, никаких старых снимков/описаний |
| prune | TaskRecord, RegularRecord или OccurrenceRecord с оставшимся деревом, без удалённого пункта |
| stop_regular | Только цель regular, payload=null |
| rollover | Только regular, новый текущий экземпляр с детерминированным корневым UUID, все отметки false, completed_at=null |

prune отделён от put ради барьера удаления подзадач. Проверка изменения состава
ID требует прежнего серверного состояния: put не должен удалять старые пункты,
prune должен действительно удалить допустимые пункты, restore — явно вернуть.
Сам кодек видит только запрос и не доказывает отсутствие удалённого текста в
оставшихся пользовательских строках. delete корня всегда без тела.

## Квитанция

Оболочка `version:1`, `kind:receipt`, `data` с точными полями:
op_id, device_id, server_id, request_hash, status, revision, delete_epoch, error.
request_hash — 64 строчные hex-цифры SHA-256 канонического encode_operation.
Это связывание с содержимым, не подпись/аутентификация или доказательство записи.
Пробелы JSON/порядок ключей при повторном декодировании не меняют хеш.

status=applied требует revision>0/error=null; status=rejected требует один код:
stale_epoch, stale_revision, deleted, not_found, already_exists,
invalid_transition, quota, generation_changed, operation_conflict.
Других строк ошибки, тела запроса, старого payload или заголовка задачи нет.

verify_receipt проверяет совпадение op/device/server/hash. Для applied ревизия
строго больше base_revision; delete/restore/prune/stop_regular увеличивают epoch
на один, create/put/rollover сохраняют его. rejected остаётся отклонённой операцией,
не считается применением. Проверка работает и для прежней сохранённой квитанции,
когда сервер позднее уже изменился: она относится к исходной операции.

Сервер ещё должен реализовать проверку owner/сессии, постоянный поиск по op_id,
возврат прежней квитанции для того же хеша и отказ для другого хеша. Здесь нет
таблицы повторов и невозможно обещать идемпотентность реального обмена.

## Регулярность и переходы

rollover_record(previous, day) строит только кандидата для более позднего дня
расписания. Новый root=uuid5(rule_id, "occurrence:"+ГГГГ-ММ-ДД); ID потомков
детерминированы root/позициями. Названия/поля/веса сохраняются, выполнение
сбрасывается. Файлы/календарь/фокус в DTO отсутствуют. Источник не меняется.

Два одинаковых шаблона/правило/день дают одинаковое дерево; различающиеся
шаблоны могут дать разное содержимое с тем же root. Поэтому сервер обязан
проверить точный base_revision/epoch для rollover и день по общей временной зоне,
сохранить выполненный прежний экземпляр один раз по (rule_id, day) и заменить
текущий атомарно; проигравший клиент получает актуальное состояние. Один кодек
не решает гонку. Он не имеет прежнего серверного состояния и общих часов.

stop_regular должен атомарно превратить сохранённый сервером текущий экземпляр
в обычную задачу и удалить правило. delete цели regular должен убрать правило
и его текущий экземпляр, сохранив нужные отметки без текста; завершённая история
подчиняется обычному лимиту. Эти эффекты ещё не реализованы. Страницы должны
выдавать согласованный результат всех эффектов, без дубля текущего корня.

Desktop пока генерирует случайные UUID своим прежним локальным путём. Новый
helper ещё не подключён: перед синхронизацией нужны переход старых расписаний,
проекция/идентичность истории, подключение принятого общего пояса и зависимости
офлайн-операций (основание rollover после ещё не подтверждённого put).
Нельзя автоматически менять основание старой операции, обходя барьер удаления.

## Ограничения и проверки

JSON UTF-8, без float/NaN/Infinity/повторных/неизвестных/пропущенных ключей;
кодеки сущностей повторно проверяют вложенный payload. Лимит 2 МиБ на операцию
или квитанцию целиком, включая оболочку. Почти предельная сущность может не
поместиться в операцию: отказ без усечения. Пакеты/пагинация — следующий шаг,
пока нет отправки 50 операций и применения страниц/курсов.

Примеры — tests/fixtures/sync_operations/v1 (4 пары запрос/квитанция).
Тесты — tests/test_sync_operations.py; ни сеть, ни настоящий профиль не нужны.
